# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Class schedule design decisions

- The app shows the real Kraków timetable for plan 1000 from a validated `public/schedule.json` snapshot. Do not show demo, preview, or sample-data labels or markers in the UI, and never silently substitute fabricated classes when the live snapshot fails.
- The selected reference is the user's dark Apple Calendar screenshot. Keep a calm, compact dark calendar layout with a desktop week view and mobile day view by default.
- The primary accent is `#FFAE00`; use it sparingly for selected dates and key navigation emphasis.
- Give Wykład, Ćwiczenia, and Konwersatorium distinct event colors. The source plan's "Forma zaj." column for 1 Oct 2026–21 Feb 2027 contains Wyk, Cw, and Konw; English classes are marked Cw. Lektorat was an invented demo category and should not appear unless a later source timetable actually uses it.
- Do not show class-type legends in the sidebar or calendar canvas. Keep an "Inne" color for an unmapped rare source form and preserve its original label in event details.
- Show class-type labels in normal Polish capitalization in event details. Keep them off event cards.
- Keep the UI data source behind `getSchedule()`. A Playwright importer reads the source's full-semester grid into `public/schedule.json`; the browser fetches that file and refreshes it while open. Do not change the calendar components to parse the source site directly.
- When a class disappears from a validated full-semester import, retain its last sourced time and details as a cancelled event labeled "Odwołane" in day, week, month, and event details. Keep it visually subdued and exclude it from active class counts. Treat edits to the same class on the same date as updates, and clear the cancellation if the source entry returns. The source does not provide an explicit cancellation flag, so explain in details that the class is absent from the current university plan.
- Show common plan classes to everyone. When no English group is selected, show classes from all parallel English groups in the calendar. Let each visitor choose a source group to show only that group's English classes, and keep that choice in local storage. The empty default and "Wszystkie grupy" option both mean all groups.
- Label the English-group options compactly as B1, B1+, B2, and C1. Keep the full source group strings as option values so filtering and saved choices remain accurate.
- Keep the English-group selector's chevron centered with consistent inset spacing. Avoid bright external focus outlines throughout the app; show a subtle neutral inset indicator for keyboard focus without a conspicuous ring after pointer clicks.
- Keep the interface free of app branding, the study-program sidebar card, and the small heading above the month title; the user explicitly removed these.
- Provide day, week, and month views. The month grid uses the same class-type colors, with a selected-day agenda on mobile.
- Use a neutral, near-black gray scale for the dark app's page, sidebar, borders, controls, and dialog. Keep `#FFAE00` as the sparing accent and the class types distinct. Do not tint the full timed grid amber for today in either theme; the user wants the header and canvas to match when the sidebar is hidden.
- The default dark theme should be close to black rather than brown. The light theme uses near-white warm gray surfaces, pale neutral buttons, and softer charcoal text; avoid the earlier brown/beige cast and heavy dark controls. Keep the theme button visible on desktop, place it in the mobile settings popover, and persist the user's choice locally.
- Wykład events use purple and Konwersatorium events use blue in both themes; Ćwiczenia stay green. Keep the surrounding calendar surfaces neutral gray and the other class-type colors distinct.
- Keep light-theme event-card hover shadows subtle; use a soft, low-opacity lift rather than the stronger dark-theme hover shadow.
- Use the typography and spacing scales from the user-provided typography and spacing skills: system sans; 12/14/16/24/30/36px type roles with 400/500/600/700 weights; 4/8/12/16/24/32/48/64/96/128px spacing. Keep the timeline's hour-to-pixel scale tied to event duration and the mobile calendar deliberately compact.
- On desktop, keep the sidebar hideable from an always-visible top-bar button. Animate the sidebar and calendar width together with a short, interruptible layout transition, remember the user's choice, and remove collapsed sidebar controls from keyboard navigation. Keep the sidebar and its toggle hidden on mobile.
- Keep the top bar free of a bottom border.
- Keep the light theme's neutral borders pale. Keep the dark theme's grid, separator, and control borders subdued and close to the near-black surfaces; preserve the colored edge that identifies each class type.
- Keep the calendar canvas within the viewport and make its timeline scroll vertically through the full day, from 00:00 to the following 00:00, on desktop and mobile.
- When the day or week timeline opens, scroll it to the current Warsaw time with some earlier hours visible above the current-time line. Preserve manual scroll position while navigating dates or switching between day and week; keep the full-day range available by scrolling.
- In the week timeline, draw the current-time line faintly across every day column and brighter with a dot in today's column, following the Apple Calendar reference. Keep the grid background neutral gray.
- Leave the corner above the time axis blank; do not show a GMT or UTC offset label in the calendar header.
- Keep the weekday date header free of top and vertical borders; its only separator is the bottom border. The timeline grid below retains its vertical lines.
- On mobile, use the separate date selector above the canvas only in day view. In week view, show the weekday/date header inside the horizontally scrolling canvas so it stays aligned with the day columns. Recycle adjacent weeks as the user scrolls horizontally in either direction, with no fixed first or last week.
- In mobile day view, show only the class count below the month/year title; the date selector already shows the chosen day. Keep the date range in week view and the full chosen date in desktop day view.
- In the mobile day selector, mark the real current date even when another day is selected: color only today's number with the theme's readable amber text token and expose `aria-current="date"`. Keep the filled amber circle for the selected day.
- In the mobile day selector, animate only the selected amber circle: the previous circle shrinks away and the newly selected circle grows over 200ms. Keep each numeral fixed at 32px with unchanged weight and position, let its color change, and disable the global pressed-button scale for those date buttons. Reduced-motion settings make the circle switch immediate.
- In the mobile month grid, use the same date treatment and circle motion as the day selector: only the selected date has the filled amber circle, while an unselected today has an amber numeral. Keep the numeral and 32px visual button still as the old circle shrinks and the new circle grows over 200ms, preserve the 44px hit area, and make reduced-motion changes immediate. Expose today with `aria-current="date"`.
- Apply the same selected-circle motion and independent today marker to the desktop sidebar mini-calendar. Keep the date numerals fixed, animate only the amber fill for 200ms, avoid a pressed-button scale, and disable the transition for reduced motion. Mark today with `aria-current="date"`, including when it appears in an adjacent month.
- Use the shared selected-date circle treatment for the sidebar mini-calendar, mobile day strip, and mobile month grid. The selected date has a filled amber circle; an unselected today has amber text and `aria-current="date"`. The old circle shrinks and the new one grows over 200ms without moving numerals, and reduced motion switches immediately. The mobile week header travels with the horizontally scrolling canvas but its dates are static.
- In day and week views at every size, the canvas date header is static and only today's date has a filled amber circle; choosing another day does not highlight it on the canvas. In desktop and tablet month view, date numbers are static rather than buttons because the classes are visible in each cell. Mark today with a filled circle, leave other dates unhighlighted, and keep the class event cards clickable. Mobile month dates remain selectable for the day agenda.
- Give mobile controls at least a 44px touch target where space permits. Keep the seven day-selector columns at least 44px wide even at 320px. Month-date circles may remain visually 32px, with nonoverlapping 44px hit areas. Keep the heading and its two icon controls on one row down to 320px; use the 24px mobile month-title size through 429px and 20px below 360px so longer Polish month names fit.
- Keep the previous/next arrow buttons on desktop, and remove them from the mobile toolbar. Do not show a separate Today button.
- The desktop theme toggle is icon-only with no fill or border in either theme and a 20px icon inside a 40px hit target. On mobile, the 44px sliders trigger opens a settings popover containing the English group selector and an appearance toggle.
- On mobile, remove the separate English group row to give the canvas more vertical space. Place the sync status and sliders triggers together beside the month/year heading, with no extra navigation row. Do not reserve a separate top-bar row. The unselected group state is a valid all-groups view, so do not mark the sliders trigger as needing attention. Close the popover on outside press or Escape, and return focus to the trigger after keyboard dismissal.
- Leave space above the entire mobile UI for iOS Safari's translucent system area: use the viewport safe-area inset plus 16px, including in installed web-app mode. Keep the page background extending behind the system area and preserve the calendar's viewport-height layout.
- On mobile, float the day/week/month view switch at the bottom center of the calendar canvas instead of keeping it in the top bar. Make the floating bar a fully rounded 280×62px pill with rounded segments, 14px labels, a more transparent surface (54% dark, 58% light), a subtly translucent selected segment, and background blur while keeping text legible. Place it 21px above the viewport bottom plus any safe-area inset, preserve its touch targets and sliding indicator, and leave enough scroll clearance to reveal late events and the bottom of the month agenda. Keep the desktop switch in the top bar.
- The view switch uses one selected indicator that slides between day, week, and month over 200ms with the existing ease-out curve. Keep its endpoints aligned exactly to the three segment buttons in desktop and mobile layouts. With reduced motion, move it immediately.
- When Day is already selected, selecting Day again returns to today's date in both desktop and mobile view switches. Keep the separate Today button removed.
- Animate the theme icon swap like the right-hand button comparison on animations.dev: the outgoing icon shrinks toward 0.8 and blurs to 2px while the incoming icon scales up and clears, with a 150ms ease-out crossfade. Pressing the button scales it to 0.97. Keep reduced-motion changes immediate and preserve the icon-only button surface.
- In the mobile day view, horizontal swipes on the canvas move one day backward or forward. The calendar content should follow the finger and settle into the adjacent day with a short transform transition; a partial swipe should return to the current day. Keep the time axis fixed, vertical timeline scrolling, event-card taps, and reduced-motion behavior working.
- In the mobile month view, horizontal swipes move to adjacent months with the same follow-the-finger, short-settle carousel behavior as day view. Keep vertical agenda scrolling, date selection, and event-card taps working. Retain the selected day number where the target month has it.
- Clip each mobile day-carousel pane at its own edges so the next day's current-time dot and other content cannot peek into the selected day when the carousel is resting.
- Separate the mobile date strip from the timeline with a bottom border only; leave its top edge borderless.
- Align the mobile date strip's weekday labels and date numbers toward its bottom border without increasing the strip's height.
- Position the weekday names and date circles toward the bottom of their 48px header, with a small gap above the bottom border.
- Set the main month name in the calendar heading at font weight 600, with the year lighter at 400.
- Keep the colored edge of class blocks restrained: 3px on timed cards and mobile month agenda cards, 2px on compact month events. Apply the edge consistently to every class type.
- Align the mini-calendar's weekday initials directly over their date columns, including at the narrow sidebar width.
- Put the class title first on event blocks, with icon-labeled time and room beneath it. Do not show the class type on event blocks; the colors and event details identify it.
- Use a small clock icon with the time range and a map pin with the room on event blocks.
- Show the room on timed event cards at every viewport width, and use the same 8px card padding on desktop and mobile.
- Use the same medium (500) font weight, line height, and per-theme color treatment for time and location metadata. Keep the class title bolder.
- Let the scrollable calendar canvas fill the space down to the bottom of the main area, without a fixed legend bar.
- Keep the event-details close button icon-only without a visible fill or border, including on hover. Preserve its mobile touch target and keyboard focus indicator.
- In event details, show the class name and metadata first. Place the class-type badge in the bottom badge row, to the left of the group badge, with matching height, padding, and text size. Keep its class color and 10% background tint; use a darker readable shade in light mode. Do not use a separate colored line above the details.
- Shade Saturday and Sunday with a subtle neutral gray across their full day/week timeline columns and month cells in both themes. Leave the day/week date headers, mobile date selector, and month weekday header plain; date circles keep their existing selected/today treatment. Preserve class-type colors.
- Host the shared schedule on GitHub Pages. Build with the repository base path and fetch the timetable snapshot relative to that base. Run the importer every hour in GitHub Actions and publish a `sync-status.json` heartbeat after every successful check, even when timetable data is unchanged. Run push deployments from the last validated snapshot so a temporary source-site failure does not block UI releases or publish partial data; scheduled and manual sync runs should still fail visibly when validation fails. Show the last successful check in a separate mobile info popover beside the settings trigger and in the desktop info popover; keep it out of mobile Settings. Show a small warning dot only for delayed, failed, or unavailable checks. Check GitHub Actions run history only when the status panel opens so failure and skipped runs can be distinguished without polling its API for every visitor; ignore push deployment runs when assessing timetable sync health. Do not show a link to workflow history in the app.
